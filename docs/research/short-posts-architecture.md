# 短评与 Obsidian 发布架构提案

状态：提案，尚未实施。修订日期：2026-09-19。

目标是低维护、低心智负担的博客内容发布。用户已明确：桌面优先，之后支持手机；生成文件放在插件目录，不进入正常笔记列表；允许小时级发布延迟；完整短评浏览面板和跳转原文后置。个人笔记使用官方 Sync，Git 主要负责备份，但博客发布不通过远端同步整个 vault。

最终建议：插件定期检查公开内容是否变化，有变化才上传一份完整快照；现有后端保存快照并触发 Astro 静态构建。云端不安装 Obsidian、不运行 Headless Sync、不接触整个 vault。官方 Sync 和 Git 继续承担个人笔记的同步与备份。

后续能力的细化见[原文标注、稳定 ID、管理视图与 X 来源](./short-posts-editor-and-x.md)。用户已进一步确认：可靠关联的原文改动应随下一次同步自动更新；来源失联时保留身份和已公开正文，而非自动撤回。

## 用户操作到本地保存为止

在日记中选中文字，执行“发布为短评”，查看简短预览并确认。插件保存成功后提示“已保存，将自动同步到博客”。用户不需要操作文件、执行 Git 命令、手动导出或管理上传队列。

首次发布绑定明确选区，后续对可靠关联范围的编辑自动更新候选正文，下次上传后更新网站。移动原文时尽量保持关联；整段暂时消失或位置不确定时保留短评 ID 和已确认公开正文，暂停这条更新。撤回通过明确的插件命令完成，不能由来源删除推断。

完整管理页和右侧菜单可以分阶段实施，但稳定 ID 与持久锚点从开始就需要设计。数据只放在插件目录，不生成 Markdown 副本；默认通过编辑器事务与原文片段追踪范围，不往日记里插入标记。需要恢复关联时，使用同一 ID，不另建一条。

## 数据保存在插件目录

采用 Obsidian 标准的插件数据文件：

```text
vault/
  <config-dir>/plugins/<plugin-id>/
    main.js
    manifest.json
    data.json
```

生成数据不出现在 Obsidian 正常笔记列表，用户无需访问文件系统管理它。`<config-dir>` 使用实际配置目录，不写死 `.obsidian`。`Plugin.loadData/saveData` 读写插件的 `data.json`。[官方 API 定义](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

以下是基础字段示意；原文高亮与自动更新还需要持久锚点、定位状态和最近确认上传的正文，详见后续能力提案，不能仅靠此处的 path / selection 定位：

```json
{
  "schemaVersion": 1,
  "settings": {},
  "entries": {
    "stable-uuid": {
      "bodyMarkdown": "一段明确选择发布的文字。",
      "selectedAt": "2026-09-19T08:00:00Z",
      "updatedAt": "2026-09-19T08:00:00Z",
      "status": "published",
      "tags": [],
      "source": {
        "path": "日记/2026-09-19.md",
        "blockId": null,
        "selection": "一段明确选择发布的文字。"
      }
    }
  }
}
```

`published` 表示作者希望公开，不表示网站已经部署成功。ID 在首次保存时生成，独立于正文、行号和路径；修改保留 ID，撤回改为 `withdrawn`。来源信息和设置不进入上传数据。

采用单文件完整状态，不保存逐条网络操作或回执。保留写入串行化、加载校验和迁移前备份，写入失败不显示成功；解析错误不能覆盖成空集合。备份仍留在插件目录，核验现有 Git 备份是否覆盖本插件的数据文件即可，不要求发布前提交 Git。

上传状态属于设备本地信息，不与内容一起经 Sync 复制。可使用 vault 关联的设备本地存储缓存“上次确认上传的 hash、远端 revision、上次检查时间”；缓存丢失时向远端核对后恢复，不据此删除内容。凭证通过 SecretStorage 保存，`data.json` 仅保存凭证名称；它不进入备份或上传快照。[SecretStorage 文档](https://docs.obsidian.md/plugins/guides/secret-storage)

## 数据流

```mermaid
flowchart LR
  A[日记选区] --> B[插件预览与本地保存]
  B --> C[插件目录中的 data.json]
  C --> D[插件定期生成公开快照]
  D -->|有变化才上传| E[现有后端：保存完整快照]
  E -->|需要更新网站| F[Astro 静态构建与部署]
  F --> G[短评列表 / 详情 / RSS]
```

Obsidian 中关联的原文是唯一正文编辑入口；管理页负责浏览与操作，远端快照和网站是派生结果。不在博客管理端或插件管理页增加另一个独立正文编辑器。

插件只发送经过公开字段白名单转换的快照：稳定 ID、正文、标签、公开时间和撤回状态。不发送日记、来源路径、定位文本、插件设置或凭证值。凭证只用于 HTTPS 请求鉴权。服务器也校验严格的公开 schema，不能仅信任客户端已经过滤。

## 定期检查，不维护操作队列

默认在 Obsidian 运行时每小时检查一次。启动或回到前台时，如果距离上次检查已经足够久，补一次检查；也保留“立即同步”命令用于调试和偶尔需要提前更新的场景。写入内容只标记需要检查，不立即产生网络请求。

每轮流程：

1. 本地记录完整有效且来源定位可靠时，用稳定的当前正文生成公开快照；失联条目沿用已确认公开正文，尚未发布的失联条目留在本地。白名单转换并稳定排序后计算 hash。
2. 与上次服务端确认的 hash 相同则不上传。原文路径或插件设置变化不应触发上传。
3. 有变化时只发送这一份最新快照；同一设备同时最多一个上传请求。
4. 服务器确认保存后，记录本次请求捕获的 hash 与远端 revision。
5. 失败保留本地内容和旧确认信息，下轮重新发送最新快照，不要求用户再次选区。

上传途中又修改内容时，只确认已经发送的那一版，新改动留到下一轮。断网期间修改十次，只需要在恢复后发送最终状态，不补发十个操作。

关闭 Obsidian或手机挂起后，不承诺后台继续上传；下次运行再补。小时级间隔是检查目标，实际可见延迟还包括设备离线、构建排队和部署时间。正常成功保持安静，短暂失败只在插件状态中记录；持续失败或凭证失效再提供可操作提示。

## 远端只接收整份快照

复用现有 Hono 后端，增加一个受限的快照写入入口和一个供构建读取/插件核对的入口。无需逐条短评 CRUD、独立用户系统、发布凭证管理页面、操作日志表或同步服务。

| 接口                                | 作用                                                        |
| ----------------------------------- | ----------------------------------------------------------- |
| `POST /api/v1/short-posts/snapshot` | 鉴权、完整校验、保存整个快照；返回内容 hash 与远端 revision |
| `GET /api/v1/short-posts/snapshot`  | 供构建读取快照及插件核对 hash/revision；同样要求受限凭证    |

首版单人使用，可以由后端配置一个仅授权此快照接口的凭证，插件一次性配置；构建端使用服务端环境变量。凭证不是现有账户的登录 Cookie，也不能获得其他管理权限。插件通过 Obsidian `requestUrl` 发送 HTTPS 请求，不引入浏览器登录流程。[官方 API 定义](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

完整快照和少量部署状态可作为单行 JSON 记录放入已有 SQLite/Drizzle 数据库，复用持久化与备份。它是内容快照存储，不为每条短评建设领域表，也不新增对象存储或独立数据库服务。记录包含当前 JSON、hash、revision 和部署状态；上传不在数据库事务中等待网站构建。

同内容重复上传返回同一结果，不重复写入或无条件构建。请求带上插件上次取得的远端 revision；保存时原子检查，防止旧设备或乱序请求静默覆盖新快照。响应丢失后再次上传同 hash 可以直接确认成功；远端已变成其他内容时停止覆盖并保留本地数据。不要自动取最新 revision 后强行重试旧正文。

第一次连接时先核对远端；已有内容不能被刚安装插件的空集合覆盖。文件损坏、未知 schema、重复 ID 或旧 ID 无故消失都拒绝更新；撤回通过明确的 withdrawn 记录表达。单设备正常发布不需要用户处理这些内部状态。

正文、设置和凭证不写入普通请求日志。服务器拒绝未授权请求和超出大小限制的快照，构建读取端不输出读取凭证。

## 静态构建与失败恢复

当前 [Astro 配置](../../app/blog-astro/astro.config.ts) 为静态输出，[Vercel 配置](../../vercel.json) 部署静态产物；继续保留这条链路。

增加独立 `shortPost` content collection，从快照读取入口取得结构化 JSON，作为 structured-file collection 处理：整份校验成功后替换本 collection，以自己的 source revision 判断变化；渲染时只输出 published 条目。新增 HTTP raw content acquisition 入口，不改动现有文章来源。

短评、文章、页面与图片元数据各自 reconciliation，符合 [ADR 0002](../adr/0002-ingest-content-collections-independently.md)。Markdown 新增短评 rendering mode，保持 [ADR 0001](../adr/0001-keep-markdown-rendering-ui-independent.md) 的 UI 独立边界。

后端保存快照后触发现有网站部署渠道，只在公开页面需要变化时构建。同步/校验所需的撤回标记保留在远端快照中；已部署的公开页面集合没有变化时无需再次部署。部署触发只在服务端持有配置，不把部署凭证交给插件。

“快照已保存”和“网站已部署”分开记录：云端保留尚未部署的 revision，只有部署结果成功且与对应内容版本匹配才确认。触发返回成功不等于构建成功；构建必须记录自己实际使用的快照版本，不能把当前最新版本误记成已经部署。

插件有尚未完成的部署时，下次定期检查可查询并请求重试，不必再次传输未变化的正文；可复用快照入口的受限控制请求，不增加独立 API 服务。部署状态通过现有平台查询或既有流水线回报核对，具体方式在接部署时选一种。等待平台完成不阻塞本地保存，Obsidian 关闭也不取消已触发的云端构建。

同一时间只允许一个受控的部署流程，防止旧构建较晚完成后覆盖新内容。失败保留现有网站，下轮检查恢复；不因为数据拉取失败而构建空页面。插件关闭期间，尚未触发或需要重试的更新可以延后，符合小时级、非实时目标；不额外增加云端定时同步服务。

列表、详情和独立 Feed 一起静态生成，建议路径为 `/shorts`、`/shorts/<id>` 和短评 Feed。更新和撤回随下一次成功部署生效。文章也会随整个网站一起构建，这是复用现有部署链路的代价；实际构建成本过高时再考虑局部 SSR。

## 个人同步与发布的边界

官方 Sync 继续同步私人笔记与插件数据，Git 继续备份；它们不传输博客发布请求，也不触发网站构建。云端无需 Obsidian 账号、解密材料或 vault 副本。

桌面优先并不等于已经支持多设备并发发布。首版按一个主要发布设备验收，设备上的自动上传开关和凭证不随插件数据同步到其他设备。手机阶段再增加设备间内容合并、同步未完成时的发布策略与冲突恢复，不借低频上传来假定冲突消失。

插件收到 `onExternalSettingsChange` 后应重新校验加载，不能用旧内存直接覆盖；发现冲突或不完整同步时暂缓上传。普通笔记同步完成不等于短评已经上线。

## 首版范围

```text
app/
  obsidian-publisher/                  # 唯一新增应用 package
  backend/src/modules/short-posts/     # 整份快照写入、读取、部署触发
  blog-astro/
    src/content.config.ts             # 独立 shortPost collection
    src/pages/shorts/                  # 静态列表、详情、Feed
lib/
  api/src/short-post/                  # 共享快照 schema 和公开字段
  markdown/src/short-post.ts           # 短评 rendering mode
```

现有 [workspace](../../pnpm-workspace.yaml) 可容纳插件包。先不新增 `publisher-core`、通用同步 SDK、Headless 运行脚本或同步 provider 抽象。

纯文本和标准 Markdown 优先。内部链接可以降级为可见文字；不自动展开其他笔记。选区外脚注、本地附件和半个代码块在预览时明确处理，不能偷偷追加日记其他内容。插件不导入整套文章渲染的 Node/Astro 依赖。

完整短评面板、跳转原文、手机、图片和 X 聚合按后续能力提案分阶段交付；持久 ID、失联保留和定位状态不作为可省略的界面功能。未来 X 使用独立来源快照，不能与 Obsidian 争相覆盖同一份来源数据。

实施顺序：桌面选区与持久化 → 完整快照接口 → 周期性按变化上传 → Astro 内容与页面 → 部署触发和失败恢复。先用测试 vault 验证，再接真实内容。

验收重点：生成文件不进入笔记列表；重启后内容还在；无变化不上传；断网后只传最新状态；上传中继续编辑不会漏掉新内容；响应丢失重试不重复构建；旧设备不能静默覆盖新快照；没有私人路径或未选正文进入上传数据；撤回在新部署中生效；快照保存成功但部署失败仍可恢复。完整管理面板不作为首版验收条件。
