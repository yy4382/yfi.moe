# 短评后续能力：X 来源、原文标注和管理视图

状态：功能细化提案，尚未实施。资料核验日期：2026-09-19。

延续[总体架构](./short-posts-architecture.md)：插件数据放在插件目录；按小时检查、有变化才主动上传公开快照；远端不运行 Obsidian Sync；博客暂用静态构建。本文细化后续能力，不意味着本轮开始实现全部功能。

用户进一步确认：标记的原文修改后，应随下一次同步自动更新博客。短评 ID 必须稳定；原文高亮和菜单、主工作区管理视图属于目标体验。

## X 数据获取：费用与维护成本分开比较

| 方法                               | 费用                          | 能得到什么                                    | 适用边界                                                   |
| ---------------------------------- | ----------------------------- | --------------------------------------------- | ---------------------------------------------------------- |
| 官方账户归档                       | 无 API 费用                   | 帖子、媒体等账户快照，包含机器可读数据        | 适合历史导入；申请后等待下载，不是周期增量接口             |
| 官方 API Owned Reads               | 当前列价 $0.001 / 返回资源    | 符合条件的本人发帖接口、分页和增量读取        | 需开发者应用及合适认证；目标用户须是认证用户且为应用所有者 |
| 第三方数据 API，例如 twitterapi.io | 当前帖子列价 $0.15 / 1,000 条 | 服务商的结构化用户帖子接口                    | 独立于 X；重复读取、每次请求最低费用和可用性需要计入       |
| Twikit、RSSHub 等非官方读取        | 工具本身可免费                | 登录态或内部接口取得的帖子，再转换为 JSON/RSS | 账号会话、接口变化和运行维护不免费；不是免维护的数据源     |
| X 官方嵌入                         | 无需建设帖子抓取管道          | 页面上的官方时间线或单帖展示                  | 不能替代自有内容集合、稳定 RSS 和离线保存                  |

官方归档需要登录、验证并等待准备，可能耗时数天；档案还包含私信等无关内容，导入器只解析帖子及需要的媒体，不能上传整个归档。先核验实际归档结构，不执行归档中的 JavaScript，不假定永久只有一个固定文件名。[X 归档说明](https://help.x.com/en/managing-your-account/how-to-download-your-x-archive)

官方当前采用按量计费。Owned Reads 包含 `GET /2/users/{id}/tweets`，条件满足时为 $0.001 / 资源；普通帖子读取列价 $0.005 / 资源。若每月只有 100 条新帖、每条仅通过符合条件的接口取得一次，则新帖基础读取成本约 $0.10；这不是包含资料查询、补抓、旧帖复核等在内的总价估计。同一资源按 UTC 日去重的规则也不能代替增量设计。[X 计费](https://docs.x.com/x-api/getting-started/pricing)

twitterapi.io 提供独立的用户最新帖子接口，当前每页最多 20 条。计费页列有每次请求至少 $0.00015；不能只用“新增条数 × 单价”估算周期抓取。例如每小时反复取得 20 条、每月按 30 天计算，在每次均按返回条数收费的假设下约为 $2.16。它的单条价格更低，不代表这种轮询模式总价更低。[服务商价格](https://twitterapi.io/pricing)、[用户最新帖子接口](https://docs.twitterapi.io/api-reference/endpoint/get_user_last_tweets)

Twikit 项目提供不使用官方 API key 的用户帖子读取和 cookie 登录示例；RSSHub 的 Twitter 路由也存在，但其源码列有认证配置，并不是无需任何条件的公共 RSS。项目存在不等于已证明今天对用户账号稳定可用，本轮没有登录用户账号实测。[Twikit](https://github.com/d60/twikit)、[RSSHub 路由源码](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/twitter/user.ts)

官方嵌入支持公开账户时间线。它适合展示，但不作为博客自己的帖子数据库或 RSS 来源。[X 时间线嵌入](https://help.x.com/en/using-x/embed-x-feed)

结合“维护负担低”的目标，建议历史数据用归档导入，后续新帖优先评估官方 Owned Reads；如果完全不接受 API 费用，可以先做不定期归档导入。第三方 API 可作为价格备选；免费抓取只有在愿意维护登录态和接口兼容时才作为主路线。

### 不依赖获取方式的来源模型

- 外部帖子 ID 保存为字符串，建立 `(provider, accountId, externalId)` 来源映射；切换归档/API/抓取不能重新生成本站 ID。
- 处理 X 的编辑版本链，将同一条帖子的编辑版本归入同一本地记录；不能按新正文 hash 新建帖子。
- Timeline 有历史数量限制；文档列出普通用户发帖最多最近 3,200 条，排除回复时还有更低限制，因此历史导入优先归档。
- 增量读取不能发现所有旧帖编辑、删除或转私密；需要独立复核，网络/权限错误不直接当删除。
- 默认聚合本人原创内容，回复、转帖、引用帖和长帖/thread 的范围单独配置；普通 X 文本不能未经处理直接解释为 Markdown。
- Obsidian 和 X 各自拥有来源快照，聚合时合并；一个来源更新不得清空另一个。两个平台相似正文只提示关联，不自动去重合并身份。

这些是导入行为，不增加新的交互式发布平台。[X Timeline 集成指南](https://docs.x.com/x-api/posts/timelines/integrate)

## 原文标注：通过编辑器扩展绘制

编辑模式和 Live Preview 使用 Obsidian 的 `registerEditorExtension` 接入 CodeMirror 6。高亮用 mark decoration，附加控件由独立视图层绘制；不把高亮写成 Markdown 的 `==...==`，不靠反复修改编辑器 DOM 或扫描整本 vault 实现。[Obsidian Decorations](https://docs.obsidian.md/Plugins/Editor/Decorations)

建议体验：轻量背景高亮标出实际发布范围，右边留一个批注入口，点击打开 Obsidian Menu。菜单包含取消发布、复制永久链接、打开管理页、查看同步状态；失联条目提供重新关联原文。撤回后保留身份记录，重新发布默认沿用原 ID。

右侧按钮需要适配长段落折行、滚动、折叠和窄窗口。优先验证宿主内置 CodeMirror 是否支持右侧 gutter；当前上游已有 `side: "after"`，但不能假定 Obsidian 捆绑版本相同。若使用 gutter，应额外核验交互和无障碍：上游 gutter 容器存在 `aria-hidden`，不能把唯一可操作入口埋在那里。必要时使用独立、可聚焦的右侧控件层，并提供命令/键盘操作。[CodeMirror gutter 源码](https://github.com/codemirror/view/blob/main/src/gutter.ts)

只渲染视口附近的按钮；布局测量与写入分开，避免每次输入重排全文。点击菜单不能改变选区、插入正文或打断中文输入法；多条标注共用一行时聚合入口，不重叠覆盖。

阅读模式需要另做 Markdown 渲染层映射。渲染后的字符位置不等于原始 Markdown 的偏移，不能复用编辑器 DOM 偏移；先做好 Source/Live Preview，再支持阅读模式。两种展示层必须共用同一份标注记录。

## 稳定身份与原文位置分离

核心保证：短评一旦创建，就有持久 ID。它不会因为正文、位置、文件名、来源定位或渲染方式变化而重建。

| 概念         | 生命周期                                                         |
| ------------ | ---------------------------------------------------------------- |
| `postId`     | 创建一次；供网站、RSS、来源菜单和管理页使用                      |
| 原文 anchor  | 记录这条内容目前关联哪个文件、哪段文字，可以移动、失联和重新关联 |
| 发布意图     | published / withdrawn，只由明确操作改变                          |
| 原文定位状态 | linked / missing / ambiguous，与发布意图独立                     |
| 正文版本     | 随可靠关联范围中的修改变化，不进入永久 ID                        |

建议扩展本地记录，保存当前候选正文、最近确认上传的正文、首次发布时间，以及 anchor 的路径、范围、原文片段、前后文和定位状态。锚点与前后文全部留在插件数据中，不能进入公开快照。

`from/to` 是当前文档版本下的坐标，不是身份。CodeMirror 偏移按其 UTF-16 语义处理；中文、组合字符和 emoji 不能用字节长度或视觉字符数直接换算。用于恢复匹配的归一化文本与实际发布的原始 Markdown 分开保存。

### 第一层：连续编辑时跟随事务

在 StateField 中维护锚点数据，依据 transaction 的 changes 映射范围。装饰只是锚点的显示结果，删除装饰不等于删除短评记录。

在标注前插入文字、在范围内修改几个字、删掉一部分文字，都应直接映射原 anchor，保留 `postId`。整段被一次非空替换时，如果事务明确替换的是原标注范围，也可以视作同一条内容的改写；不能只因新旧文字相似度低就换 ID。

范围边界需要定义明确规则：范围内的修改纳入正文；边界上来自范围内光标的同段落续写可以扩展；在范围外插入新段落不扩展。无法确定的跨边界粘贴、跨标注合并或多光标操作，应保留 ID 并暂缓这条自动更新，不能默默吸入旁边的日记。

通过 CodeMirror 的 undoable effects 将锚点删除/恢复信息配合编辑撤销记录保存。单纯 `range.map(changes)` 不足以处理整个范围消失后的恢复；也不能给 Obsidian 再安装第二套 history 或替换原有 undo 行为。实际宿主中的撤销分组、redo 和多视图行为必须验证。[CodeMirror Reference](https://codemirror.net/docs/ref/#commands.invertedEffects)、[history 源码](https://github.com/codemirror/commands/blob/main/src/history.ts)

### 第二层：整段删除后保留失联记录

整段删除时，把 anchor 变成 missing，持久保留原 ID、删除前正文、位置和前后文。不能把范围简单压缩成零宽后，默认吸收该位置后续输入的所有文字。

用户撤销删除时，优先通过对应的历史操作恢复原 anchor；如果随后改几个字，继续更新同一条短评。撤销历史不保证跨关闭/重启完整保留，因此还需要下一层恢复。

手动重新插入或剪切后粘贴时，结合最近删除位置、原文片段、前后文、文件身份与编辑顺序找候选。对于同一位置附近、内容仅小改且候选唯一的情况，可以在经过测试标定后自动恢复；有多个相似候选时不猜。所谓“最近删除窗口”只影响自动候选查找，不是 ID 的有效期。

没有找到来源也不取消发布。已上传的条目继续保留最近确认的公开正文，暂停这条更新；其他正常条目照常上传。全量快照不能把 missing 条目漏掉，否则会被误解为删除。尚未上传过的条目先留在本地，等来源恢复后再发布。

自动恢复应等输入法 composition 结束、编辑短暂稳定后再生效。不能在重新输入到一半时把一个相似但不完整的片段当成恢复结果。

### 第三层：重启、外部修改与重新关联

在插件数据中保存 selected text 的 exact、prefix、suffix，再辅以原位置、文档版本和可用的 block ID。W3C TextQuoteSelector 使用同类的文本与前后文组合，但这里仅借鉴恢复思路，不宣称本地偏移格式完整实现该标准。[Web Annotation Data Model](https://www.w3.org/TR/annotation-model/#text-quote-selector)

恢复顺序：已观察到的事务/文件 rename → 校验过的原坐标 → 唯一的原文与上下文匹配 → 受限的近似候选 → 人工重新关联。精确字符串重复出现时也需要上下文，不能选第一次命中。文件路径发生变化时，运行中的 rename 事件可以维护映射；插件关闭期间的改名并大幅改写不能保证自动识别。

只检查已关联文件及有明确证据的目标，不在每次按键后全文模糊扫描整个 vault。打开多个同文档标签页时共享文档记录，使用文档版本去重更新；不能让每个视图各自写一份持久状态。Sync、外部编辑器、格式化插件造成的更新如果没有可用事务，应进入恢复流程，而非套用失效坐标。

重关联操作为：在原文选中正确内容 → 选择“关联到现有短评” → 指定那条失联记录。保留 `postId`、首次发布时间、URL 和 RSS GUID，重新启用后续自动更新。

没有编辑历史、原始标记或唯一上下文时，两个相似段落的身份可能无法区分。这里能保证“既有 ID 不丢、不会误发、可恢复”，不能诚实地保证任意编辑之后都零交互地自动识别。

### 是否在原文嵌入标识

默认先使用插件目录中的锚点，不修改原文。原文本来就有 block ID 时可以借用，但 block ID 面向块，不能单独精确描述任意划词范围。

若之后实测发现跨关闭、跨文件移动恢复频繁失败，再讨论可选的隐式 HTML 标记或显式 block 标识。它们会改变原始 Markdown，并影响复制粘贴和重复 ID；即使加标记，连标记一起删除或复制也仍需处理。不能在未经讨论时为了定位悄悄改写日记，也不把“插一个 ID”当成所有 corner case 的解法。

## 自动更新与永久链接

用户已选择：标记范围中的修改随下一次同步自动更新。正常 linked 状态下，编辑稳定后把当前范围提取为候选正文；到上传周期时再核对来源版本和边界，生成完整公开快照。

这不等于将整篇笔记加入发布范围。missing / ambiguous、未完成输入法组合或结构不完整的条目暂停更新，沿用已确认公开正文；只显式“取消发布”才撤回。短评管理页不增加第二份独立正文编辑器，编辑入口仍回到关联原文。

建议永久地址使用 `/shorts/<postId>`，列表再提供 `#short-<postId>`。只分享当前列表的 hash 不足够：随着分页或虚拟列表变化，该条可能不在 DOM 中。若要承诺 hash 链接长期可用，页面必须能根据 hash 找到并加载对应条目。

RSS 用固定 GUID，例如 `urn:yunfi:short:<postId>`，并设置 `isPermaLink="false"`；`link` 为永久地址。修改正文只改内容和更新时间，不改 GUID，也不重置首次发布时间。RSS 规范允许阅读器用 GUID 判断是否为新条目，但不同阅读器对编辑刷新和撤回的展示仍有差异。[RSS 2.0 规范](https://www.rssboard.org/rss-specification#ltguidgtSubelementOfLtitemgt)

撤回保留原 ID；重新发布同一条默认仍用原 ID。若用户明确“另发一条”，才分配新 ID。

## 管理页是主工作区的 ItemView

用户描述的是自定义视图（Custom View / `ItemView`），承载在主工作区标签页的 `WorkspaceLeaf` 中。外观像打开一份文档，但内容是插件自己的界面，无需实际 Markdown 文件，也不是 Modal 或 popover。[Obsidian 自定义视图文档](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/User%20interface/Views.md)

使用 `registerView` 注册，并通过 `workspace.getLeaf('tab')` 打开在主工作区。提供标题、图标、筛选/选中项的视图状态恢复；关闭标签页时清理订阅与 UI，不删除短评数据。可以正常并排打开原文和管理页。[Workspace API](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

内部可用 React 渲染列表与详情，不需要 iframe、独立 Web 服务或额外路由框架。UI 订阅同一份插件数据；多视图实例不能各自成为独立数据源。

建议先展示正文、来源、公开链接、更新时间，以及“待同步 / 已同步 / 来源待恢复 / 已撤回”等状态；动作包含跳转原文、复制链接、撤回、重新关联。即使正常高亮已经丢失，用户仍能从这里找到原短评。这个恢复入口比复杂筛选、统计或视觉效果更优先。

## 优先验证编辑行为，再做界面细节

最有价值的原型是一小段带固定 ID 的标注，在真实 Obsidian 编辑器里反复修改和恢复。先证明标注不会误关联，再制作完整右侧栏和管理页。

必须覆盖的测试矩阵：

| 类别       | 案例                                              | 主要断言                               |
| ---------- | ------------------------------------------------- | -------------------------------------- |
| 普通编辑   | 前方插入、范围内替换、同段落续写、两端删除        | ID 不变，范围不吸入邻接私人内容        |
| 临时删除   | 整段删除→undo→改两字；删除→手动重输→改两字；redo  | 原身份恢复，短时消失不撤回             |
| 段落结构   | Enter 拆分、Backspace 合并、列表缩进、跨段落选择  | 已定义边界规则；歧义时暂停更新         |
| 移动与复制 | 剪切到同文件/另一文件、复制段落、重复相同句子     | 复制不自动继承公开身份；候选不唯一不猜 |
| 生命周期   | 关闭重开、插件重载、外部改写、文件改名、Sync 回滚 | 失效坐标不直接使用，原记录可恢复       |
| 编辑器细节 | 中文输入法、emoji、组合字符、撤销分组、多光标     | 不切断字符，不发表组合中的临时文本     |
| 视图       | 多标签页、分屏、折叠、滚动、阅读模式、主题        | 一份身份与状态，装饰不干扰编辑         |
| 发布交叉   | missing 时同步、编辑中到达定时器、上传时继续输入  | 不漏掉已发布条目，不用错候选版本       |
| 链接与订阅 | 编辑、撤回、恢复、重关联、分页                    | 固定 URL / GUID，首次发布时间稳定      |

建议组合纯锚点状态测试、随机编辑序列不变量测试和真实 Obsidian 操作测试。DOM 截图只能验证外观，无法证明历史、原文关联与发布正文的一致性。首版仍可分阶段交付，但持久 ID、失联保留和发布/定位状态分离必须从第一份数据结构开始具备。
